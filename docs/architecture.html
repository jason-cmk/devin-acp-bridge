Devin's brain, OpenCode's face.

A small local server that makes Devin look like an ordinary OpenAI model to OpenCode. OpenCode renders the reply. Devin does the work. Neither tool knows the other is there.

01Why it exists

Problem

Devin CLI renders poorly

No syntax highlighting in fenced code. Weak headers, lists and emphasis. The terminal is not the cause: OpenCode renders the same markdown well in the same tmux pane.

Constraint

OpenCode cannot host ACP

devin acp is an ACP agent. OpenCode can be an ACP agent, but not an ACP client. So OpenCode cannot talk to Devin directly.

Solution

Translate in the middle

Speak OpenAI to OpenCode on one side and ACP to Devin on the other. No fork of either tool. Only public interfaces and config.

02The big picture

Three processes on one machine. The bridge sits between them and owns all of the translation logic.

The bridge speaks two protocols. The core job is to turn a stateless chat API into a stateful agent session, and back.
Key idea. OpenCode thinks it talks to a plain chat model. It sends the whole conversation on every request. Devin keeps state in a session. The bridge remembers which OpenCode session maps to which Devin session, and sends Devin only the newest user message.

05Session mapping

OpenAI requests are stateless. ACP sessions are not. SessionStore.plan() decides, for each request, whether to reuse a Devin session or to start a new one.

Rules

  • Reuse only when the history grew by exactly one user message.
  • Replay covers edits, retries, reverts, a bridge restart, and a devin acp crash. Devin gets the earlier turns as a transcript, so it keeps the context.
  • System messages are dropped. OpenCode's ~80 KB prompt describes tools Devin does not have.
  • The tools array is ignored. The bridge never emits tool_calls, so OpenCode never runs anything.
  • Working directory comes from the X-Devin-Cwd header (absolute and existing), else the bridge's own cwd.
  • Sessions live in memory only.

Fence safety. TurnRenderer tracks whether Devin's own text has an open ``` fence. Tool lines that arrive mid-fence are queued until the fence closes, so a tool line never lands inside a code block. Blank lines surround every block so the markdown parser keeps them apart.

08Model selection

OpenCode never calls /v1/models on an OpenAI-compatible provider. A small OpenCode server plugin fills the gap. Devin reports models only per session, so the bridge reads them from session/new.

sequenceDiagram
  participant P as opencode-plugin
  participant B as Bridge
  participant D as devin acp
  participant O as OpenCode /models

  Note over P: on load (waits up to 15 s), then every refreshMinutes (5)
  P->>B: GET /v1/models (Bearer token)
  alt catalog fresh (under 15 min, or from a real session)
    B-->>P: cached list
  else stale
    B->>D: session/new (throwaway)
    D-->>B: configOptions.model
    B->>D: session/delete
    B-->>P: [devin, claude-opus-…, swe-2-high, …]
  end
  P->>P: drop ids matching exclude (fusion-*)
  P->>O: ctx.model.transform → register devin/* models
  Note over O,B: Later, on a chat request with body.model = "swe-2-high"
  O->>B: POST /v1/chat/completions
  B->>D: session/set_config_option {configId: "model"}
  Note right of D: unknown model → HTTP 400,
new session deleted

The ID devin means "the model this session started with", so you can switch back after trying another one. Each model ID carries its default thought level, for example claude-opus-5-5-medium.

Esc in OpenCode

The HTTP request aborts. The bridge sends session/cancel. The turn ends with _Cancelled._ and finish_reason: stop.

Busy session

A second request for a session that is still running waits up to 5 s, then gets HTTP 409.

devin acp dies mid-turn

Every ACP call races against the child's exit promise. The open turn ends with "The bridge could not complete the Devin turn". The next prompt starts a new child and replays history.

10Security

Loopback only

Binds to 127.0.0.1, hard-coded. No remote access.

Bearer token

Every /v1/* call needs it. Constant-time compare. Token from DEVIN_BRIDGE_TOKEN or a 0600 file created once. Never logged.

No filesystem access

The bridge tells Devin it has no fs or terminal capability. Devin uses its own tools; the bridge touches no files.

No Devin credentials

devin acp uses its own devin auth login store.

Quiet logs

Prompts and replies are logged only with DEVIN_BRIDGE_DEBUG=1, to bridge-debug.ndjson.

Belt and braces

The OpenCode devin agent denies edit and shell, in case a tool call ever slips through.

Known trade-offs

Devin's activity is text, not native OpenCode tool cards.A real OpenCode provider package could fix this later.
OpenCode undo reverts the transcript, not Devin's file edits.Use git.
No interactive approval prompt in the OpenCode UI.Use policy.json and Devin's own config.
Images in prompts are not forwarded.Devin supports them; possible follow-up.
